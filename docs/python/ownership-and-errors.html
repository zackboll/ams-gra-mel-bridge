Ownership and errors

The safe interface distinguishes immutable values, native owners, weak channel views and observations of asynchronous work. These distinctions determine what remains valid after close and which operations require application synchronization.

What an object owns

ObjectLifetime contract
Frames, metadata, capabilities and result recordsPython-owned scalars, strings, bytes and nested immutable values. Returned snapshots remain valid after owner closure and actual provider unload.
{{api:Session}} and typed channel ownersExplicit native ownership. Children do not keep Python parent objects alive; the native graph retains provider resources/code as required by active work.
{{api:ChannelView}}Only a native weak-view wrapper. It retains no typed source, Session, provider channel or library. A surviving view cannot prolong the source channel's lifetime.
Request ownersAn admitted native request is independent of its Python parents. Closing the public observer does not cancel pending provider work or guarantee provider unload.
Metadata receiversIndependent native consumption state and a bounded FIFO. Closing a receiver stops its consumption, not the parent channel or callback registration.

is_open reports local handle ownership. It is not a test for enablement, completion, callback admission, hardware health or safe unloading. In particular, a {{api:ChannelView}} can remain open after its source disappears, while its channel operations fail with ErrorKind.PROVIDER_FAILED. Closing the weak wrapper remains independent.

Prefer orderly local cleanup, while retaining the actual native lifetime contract: a child may outlive the Session object; queued callbacks can drain after typed-channel teardown; and an admitted request may retain the provider until its work settles. Failure paths can deliberately retain uncertain native graphs. Python does not infer quiescence or force unloading.

Close and context managers

Use the documented factory instead of constructing an owner class directly. Explicit close() reports cleanup errors. Finalizers are best-effort and non-raising, so they cannot replace deterministic cleanup and error handling.

OwnersCleanup idiom
Session, ImageStream, ControlChannel, StackedChannel, HealthStatusChannel, InstrumentationChannel, RFAdmin and ChannelViewSupport with. Entry returns the already open owner; Start or Enable remains explicit.
All public metadata receiver classesSupport with through their declared or inherited context protocol.
{{api:NavigationRequest}} and {{api:InstrumentationRequest}}Support with as well as explicit close.
{{api:ModeRequest}}, {{api:ReturnRequest}} and {{api:CommsRequest}}Do not implement a context manager. Close explicitly, normally in finally.

For the binding's context managers, normal exit reports close failures. If the body already raised, cleanup preserves that original exception. Closing a weak view only releases its wrapper. Closing a metadata consumer does not reopen a consumed registration attempt.

Close failure does not have a universal retry rule. The native operation may already have consumed the handle. Some retained handles are explicitly retryable; other owners suppress further native attempts once consumption is uncertain. For example, {{api:StackedChannel.close}} recognizes a specific retained detach failure, {{api:OpticalDistortionMapStream.close}} guards against uncertain repeat release, and {{api:RFAdmin.close}} consumes its handle even if shutdown fails. Follow the concrete owner's contract rather than adding a generic close-retry loop.

Submission, waiting and admission

Successful submission means a request was admitted. It does not establish that the command completed or that hardware changed state. Each request's wait(timeout_ms) returns a terminal value or raises a structured failure. Zero polls; timeouts are finite unsigned 32-bit millisecond values (0 through 4294967295), and Boolean values are rejected.

A timeout preserves the request owner and does not cancel work. Terminal results are cached natively and can be observed again while the owner remains open. Closing the request releases only the public observer. Pending work can continue to occupy admission capacity; closing an observer is not a way to turn the Session's admission limit into a cancellation mechanism.

Command callbacks and request futures are independent paths. Matching IDs in a CommsTest, Instrumentation or navigation callback do not cause Python to complete a future. There is no implicit correlation, replay or retry service.

Distinguish results from failures

ObservationInterpretation
A *Rejected recordA terminal provider MEL rejection with a {{api:MelErrorCode}} and description. It is a returned result, separate from a bridge failure.
ReturnCompleted(CommandReturn.FAIL)A normal completed Return value. Inspect {{api:CommandReturn}} rather than treating every completion as success.
RFAdmin.command_state(...) returns FalseNormal provider refusal. A True result means acceptance, not confirmed hardware transition.
{{api:MelError}} with TIMEOUTThe requested observation did not become available within the wait. No cancellation is implied.
STREAM_STOPPEDThe receiver's producer has stopped and no queued result remains, according to that receiver's lifecycle.
PROVIDER_FAILED, PROVIDER_EXCEPTION or another {{api:ErrorKind}}A local/native/provider operation failed. Preserve the structured details and consult the operation's ownership contract.

MelError exposes kind, diagnostic, diagnostic_required and native_status. Local validation errors can have no native status. Native diagnostic capacities count UTF-8 bytes including the terminating NUL. Direct operations use a fixed diagnostic buffer; if the message does not fit, the error preserves the status and required size, with diagnostic=None. The binding does not repeat a side effect to fetch a longer message. Request waits can retrieve complete diagnostics from their cached terminal result.

{{api:NucOpenError}}, {{api:CameraResponseOpenError}} and {{api:OpticalDistortionMapOpenError}} additionally expose registration: a separately published {{api:CommandReturn}}, or None when no known Return was available. This is distinct from the bridge error kind. Optional registration returning NOT_SUPPORTED and one returning FAIL remain distinguishable.

Most explicit input validation uses MelError. Tagged immutable models also enforce exact payload/category types with TypeError, and ordinary Python call errors retain their normal exception types. Malformed native values can raise PROTOCOL_INCONSISTENCY or INVALID_UTF8; invalid provider data is not silently repaired.

Synchronization and value fidelity

Externally serialize operations on one owner, including receive/counters/close, wait/close, and channel enable/submission/close. Serialize callback registration against conflicting parent operations such as Start, Stop and Close. At most one receive may consume a particular ImageStream at a time. The GIL does not satisfy these native ownership contracts; the package adds no background Python workers or owner locks.

Returned collection order and duplicates are preserved. Timestamps retain their signed nanosecond representation without an inferred epoch. Floating-point values are copied without unit conversion, normalization or physical-quality checks; the specific value type documents any stated units. Capability enums {{api:PixelFormat}}, {{api:SensorType}}, {{api:ChannelType}}, {{api:MetadataCapability}}, {{api:BandType}} and {{api:CoordinateSystem}}, as well as {{api:MelErrorCode}}, can preserve unknown uint32 values. That preservation does not make an otherwise unsupported payload or operation valid.
